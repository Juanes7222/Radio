# Load testing harness (k6)

The scenarios live in `scenarios/` and the shared helpers in `lib/`. `run.mjs`
is the only entry point: it resolves a profile, validates the selected path,
stamps every run with a marker, starts one or more k6 processes and writes
incremental JSON output to `reports/`.

k6 is a native binary, not an npm dependency. Install it with
`winget install k6` and check `k6 version` before any run. `pnpm exec k6` does
not work. The static check is `pnpm load:typecheck` (JavaScript with
`checkJs`); the local logic tests are `pnpm load:test`.

## Profiles

| Command | Profile | Purpose |
| --- | --- | --- |
| `pnpm load:smoke` | `smoke` | Liveness of the selected path. |
| `pnpm load:reads` | `public-reads` | Cheap public reads, cold/warm cache. |
| `pnpm load:search` | `search-isolated` | `/api/search` with a hot cache. |
| `pnpm load:writes` | `public-writes` | Guarded prayer and feedback writes. |
| `pnpm load:admin` | `admin-reads` | Panel reads with a static JWT. |
| `pnpm load:workers` | `worker-reads` | Worker and panel protocols. |
| `pnpm load:capacity` | `capacity` | Staged pure public capacity. |
| `pnpm load:capacity:mixed` | `capacity-mixed` | Staged representative mix. |

Every command accepts `--path edge|origin`, `--vus N`, `--duration T`,
`--instances N` and `--vus-max N`. The `--path` flag overrides `K6_PATH`.
Capacity profiles take their VU budget exclusively from `--vus-max`
(`K6_VUS_MAX`); `--vus` is ignored there. Other profiles use `--vus`.
`--instances N` splits a capacity run into N processes.

## Environment

| Variable | Meaning |
| --- | --- |
| `K6_PATH` | `edge` (default, through nginx) or `origin` (direct to the VPS). |
| `K6_BASE_URL` | Edge URL, e.g. `https://lavozverdad.com`. Required for `edge`. |
| `K6_ORIGIN_URL` | Public IP and real port of the backend. Required for `origin`. Loopback is rejected. |
| `K6_VUS` | Virtual users for non-capacity profiles. |
| `K6_DURATION` | Overrides the scenario duration. |
| `K6_VUS_MAX` | VU budget for staged capacity profiles. |
| `K6_INSTANCE_ID` | Set by `run.mjs` for each child process. |
| `K6_MARKER` | Unique stamp generated by `run.mjs`, printed on stdout and used to clean up write rows. |
| `K6_ALLOW_WRITES` | Must be `1` before `public-writes` can start. |
| `K6_ADMIN_TOKEN` | JWT minted inside the VPS, never `JWT_SECRET`. |
| `K6_WORKER_SECRET` | Shared secret for worker endpoints. |
| `K6_PANEL_SECRET` | Shared secret for `/panel-api`. |

`origin` needs a temporary firewall rule on the VPS that allows the
operator's public IP on the real backend port. Confirm the port with
`ss -lntp | grep node` and verify with `curl.exe` before measuring. No SSH
tunnel: it adds a hop and corrupts the latency measurement.

## Static secrets and the admin token

Run `scripts/loadtest/auth/mint-admin-token.mjs` **inside the VPS**, with the
`radio-backend` environment loaded. It picks an active admin account with
`dashboard`, `feedback` and `youtube` permissions, signs a short-lived HS256
token with `sub` and `tv`, and prints only the token to stdout. Copy that token
to `K6_ADMIN_TOKEN` on the operator machine. `JWT_SECRET`,
`WORKER_AUTH_SECRET` and `PANEL_SECRET` never leave the VPS. The panel reloads
permissions from the user row on every request, so a 401 means wrong `sub`/`tv`
and a 403 means the chosen row lacks a permission.

`run.mjs` refuses to start `admin-reads`, `worker-reads` or `capacity-mixed`
without the required secrets and exits 4.

## Guarded writes

`public-writes` starts only when `K6_ALLOW_WRITES=1` and
`K6_EMAIL_CHECK_COMMAND` is set. The check command must print the effective
value of `PRAYER_EMAIL_RECIPIENTS` from the `radio-backend` process; empty
output means the variable was emptied in Infisical and the backend was
restarted. Without both guards the orchestrator exits 2 or 3 before starting
k6, so no report is written. `K6_FEEDBACK_CATEGORY` is resolved from
`packages/types/src/feedback.ts` by the orchestrator, because k6 cannot import
a TypeScript package directly.

Each prayer insert upserts a `Device` and broadcasts an SSE event. Both count
as load: open admin panels will receive false petitions during the window.
Use `node scripts/loadtest/lib/cleanup.mjs <K6_MARKER>` to print the three
DELETE statements, then run them in a single `sqlite3` transaction on the VPS.
The marker is printed by `run.mjs` at the start of every run.

## Throttling and the stop switch

k6 assigns request tags before the response arrives, so a 429 cannot
retroactively change the tag on `http_req_failed`. The harness marks 429 as an
expected response with `http.expectedStatuses({ min: 200, max: 399 }, 429)` and
counts those events in `throttled_requests`. The
`http_req_failed{throttled:no}` threshold from the plan stays as a guard, but
the exclusion itself is performed by the response callback, not by the tag.
Read 429s as nginx throttling, never as a backend error.

Create `scripts/loadtest/.stop` while a run is active to terminate it. On
Windows `child.kill()` does not deliver a clean signal to k6: a run stopped
this way is **truncated**, `handleSummary()` may not run, and stdout is not
evidence. The valid evidence is the incremental JSON in `reports/`, which
contains `Point` events up to the interruption. `run.mjs` removes the sentinel
file on detection.

The complete maintenance-window procedure is in `docs/runbooks/load-testing.md`.
