# Backend Context

## Stack

- Express
- Prisma
- pnpm
- TypeScript-first

## Backend conventions

- Keep route handlers thin.
- Put business logic in services.
- Keep Prisma access isolated from HTTP handlers.
- Validate external input before it reaches business logic.
- Validate environment variables before using them.
- Prefer explicit error handling and predictable response shapes.
- Do not leak internal stack traces or raw database errors to clients.
- Keep request parsing, validation, business logic, and persistence separate when that improves clarity.
- Use small, focused modules.
- Prefer incremental changes over broad refactors.

## Layout (as of Aug 2026)

- `src/index.ts` — bootstrap: dotenv, Infisical secrets (dynamic imports after secrets load), scheduler, HTTP server, worker WS server, job dispatch interval, YouTube channel subscriptions.
- `src/app.ts`, `src/server.ts` — Express app assembly and listen (timeouts 600s).
- `src/config/` — env validation + per-domain config modules, aggregated in `index.ts`. Required env vars throw at import time, so config must be imported after secrets are loaded (index.ts uses dynamic imports).
- `src/shared/` — logger, errors, constants, storage (local fs), utils (date, pagination, escape-html, sanitize, text, xml-parser).
- `src/infrastructure/` — database (Prisma), firebase, email, secrets (Infisical).
- `src/modules/` — azuracast, auth, bible, backups, devices, feedback, health, locutor, live, prayer, programs, rotation, schedule, webhook, workers, youtube. Each module owns its routes/services/jobs.
- `src/jobs/scheduler.ts` — registers nightly, hourly, folder cleanup, playback, job recovery.
- `src/swagger.ts` + `src/swagger-output.json` — regenerated by `pnpm run build`.

## Listener opinions (Oct 2026)

A third public submission channel next to song requests and prayer requests: a
listener writes an opinion, a suggestion, a question or a problem report.

- **Nothing is published.** The row lands in the team inbox and stays there. There
  is deliberately no `publishedAt` column, no public read endpoint and no public
  wall. Do not add one without an explicit product decision: the page's promise
  ("no se publica") is the reason people will write honestly.
- Model: `FeedbackMessage` (`feedback_messages`) in
  `prisma/schema/feedback.prisma`. `categoria` and `estado` are plain `String`
  because SQLite has no enum; the narrow unions live in
  `packages/types/src/feedback.ts` and `feedback.service.ts` `toFeedbackMessage`
  is the only place the two are reconciled (it also emits the ISO dates the
  shared types declare).
- `nombre` and `contacto` are **optional**. There is no `deviceId` foreign key:
  the prayer module needs one because the app can list your own petitions, and
  this one has no such screen, so the column would be unused data.
- Module `src/modules/feedback/`: `feedback.validation.ts` (pure, returns
  `{ ok: true, data } | { ok: false, error }` in Spanish), `feedback.service.ts`
  (Prisma access), `feedback.routes.ts` (public POST), `feedback.admin.routes.ts`
  (guarded with `router.use(requireAuth, requirePermission("feedback"))`).
- Endpoints: `POST /api/feedback` public, no auth. Admin: `GET /admin-api/feedback`
  (paginated `{ rows, total, page, totalPages, counts, unreadCount }` with
  `estado` / `categoria` / `search` filters), `PUT /admin-api/feedback/:id`
  (estado only), `POST /admin-api/feedback/:id/read`, `DELETE /admin-api/feedback/:id`.
- Permission `feedback` in `packages/types/src/admin.ts`. `SUPERADMIN` and `ADMIN`
  derive it at runtime; a `USER` row needs an explicit
  `PATCH /admin-api/users/:id`. The admin sidebar entry lives in the **Audiencia**
  group of `NAV_SECTIONS` (`AdminLayout.tsx`), next to Solicitudes and Oración.
- **The inbox polls itself every 60 s** from the panel, so `/admin-api/feedback`
  is in `SILENT_LOG_PATHS` in `app.ts`; without it every poll writes a morgan
  line into the PM2 log the panel itself reads.
- `consent: true` is required by the validator. The form links to
  `/info/data-treatment`, the only document with `requiredInApp: true`.
- **Known gap: the public POST has no rate limit.** `POST /api/prayer` does not
  have one either. An IP-keyed limiter is not the answer here: behind nginx with
  `trust proxy = 1` an IP-keyed counter can collapse into a single global bucket
  (see "Behind nginx"). A per-`deviceId` throttle is the correct shape if this
  ever needs closing, and it would mean reintroducing the FK.
- `packages/api` exposes `submitFeedback(apiBaseUrl, payload)` so the web page
  and the mobile screen share one implementation; it returns a discriminated
  `{ success: true } | { success: false, errorMessage }` union so callers render
  an inline error instead of crashing.

## Prayer answer read receipt (Oct 2026)

A listener needs to know an answer is waiting, and the push notification is not
a guarantee: it needs a registered FCM token, which a first run does not have
until `registerDevice()` succeeds.

- **`readAt` and `answerReadAt` are two different audiences and must stay that
  way.** `readAt` is the station team's unread marker; `GET /api/prayer` counts
  `readAt: null` for its `unreadCount` and the admin panel stamps it through
  `POST /:id/read` and `POST /bulk/read`. `answerReadAt` belongs to the person
  who wrote the petition. Before this change the mobile detail screen wrote
  `readAt` too, so opening a petition on a phone cleared the admin inbox badge;
  it now writes only `answerReadAt`. Do not fold the two columns back together.
- `PUT /:id` resets `answerReadAt` **only when `respuesta` changes to a
  different non-empty value**. A rewritten answer is new content and goes back
  to unread; a plain `estado` edit leaves the receipt alone so the badge does
  not nag on a bookkeeping change. The existing "only notify when the response
  text changed" rule for FCM uses the same comparison.
- `POST /api/prayer/:id/answer-read` requires a valid `deviceId` and enforces
  ownership inside the `updateMany` WHERE clause rather than a read-then-write,
  which makes it idempotent and free of a TOCTOU window. A wrong device gets a
  **404, not a 403**, so the route does not confirm the id exists. A missing
  `deviceId` fails closed — there is nothing to prove ownership with.
- `GET /api/prayer/my/:deviceId` returns `{ rows, unreadAnswerCount }`. The
  count lives in the same payload the list already fetches rather than in a
  separate polling endpoint, and `unreadAnswerCount` is derived from the same
  predicate the client uses (`respuesta` non-empty and `answerReadAt` null).
- Migration `20261012000000_add_prayer_answer_read_at` **backfills** rows that
  already had a response: they predate the marker, and leaving them NULL would
  hand every existing device a full inbox of badges the day the app ships.
- Still true: `/my/:deviceId` and the read endpoints are unauthenticated. The
  `deviceId` is a bearer capability — knowing one returns every petition that
  device wrote, including the private `respuesta`.

## Programs (Oct 2026)

Programs produced outside the station team (a guest recording, a talk show).
Each program owns an AzuraCast sequential playlist plus two library folders,
and every uploaded episode is composed, tagged, queued once and archived on
its own.

- Models: `Program` (`programs`) + `ProgramEpisode` (`program_episodes`) in
  `prisma/schema/programs.prisma`. Module `src/modules/programs/` with
  `program.routes.ts`, `program.service.ts`, `program.episode.service.ts`,
  `program.audio.service.ts`, `program.artwork.service.ts`,
  `program.slotFinder.service.ts`, `program.temp.ts`, `program.validation.ts`,
  `program.playback.job.ts`.
- Permission: new `programs` entry in `packages/types/src/admin.ts`
  (`AdminPermission`, `ADMIN_PERMISSIONS`, `ADMIN_PERMISSION_LABELS`).
  `SUPERADMIN` and `ADMIN` derive it at runtime; existing `USER` rows need an
  explicit update through `PATCH /admin-api/users/:id`.
- Tagging in the public schedule is NOT a column on the program: the playlist
  name is the schedule item title, so `schedule/categorizer.service.ts` already
  tags it from the `keywords` of a `ScheduleCategory`. A `category_id` column
  existed and was removed because nothing ever read it.
- **The program is driven by a playlist the station already owns.** `Program.playlistId`
  points at a playlist of AzuraCast chosen in the panel, or at one the backend
  creates when the admin picks "Crear una nueva playlist". AzuraCast is what
  actually plays it, so `POST /` and `PUT /:id` validate the target with
  `playlistBlockingReason` (`azuracastPlaylist.service.ts`): it must have
  `source === "songs"`, be enabled and be sequential. A rejected playlist comes
  back as a 409 naming the reason, and `Program.playlistWarning` repeats it on
  every read so drift edited by hand in AzuraCast is visible in the panel.
  Changing the playlist also moves the episodes still in the queue, so none are
  left behind in the old one.
- **`play_full_cycle` does not exist in current AzuraCast** and neither does
  `shuffle_enabled`: both were removed from `StationPlaylist` upstream. A
  sequential library playlist already drops an item once it has played, which is
  what the archive detection relies on, so `createPlaylist` sends only fields
  that still exist (`name`, `type`, `source`, `order`, `is_enabled`,
  `include_in_requests`, `include_in_on_demand`, `avoid_duplicates`).
  Do not reintroduce the old flags: they would be ignored by the API and would
  look like a guarantee that is not there.
- Folder layout in the AzuraCast library:
  `<PROGRAMS_ROOT_FOLDER>/<slug>/NO REPRODUCIDOS/<yyyy-mm-dd> - <titulo>.mp3`
  for pending episodes and the same name under `REPRODUCIDOS` once aired. The
  date prefix keeps the folder order chronological, which matters because the
  archive job moves files rather than rewriting playlist order. Directories are
  created with `PUT /station/{id}/files/mkdir`.
- Composition happens before the upload, not in the player: `program.audio.service.ts`
  joins `[intro?, body, outro?]` with the ffmpeg concat demuxer, re-encodes to
  128 kbps / 44.1 kHz / stereo (the sources are non-professional recordings with
  mixed sample rates, so a stream copy would skip on some players) and applies
  the optional `fadeSeconds` edge fade. It uses `execFile` with an argument
  array, not a shell string, unlike the older `locutor/tts.service.ts` helpers.
- **Per-episode repair options**, chosen in the upload dialog and stored on
  `ProgramEpisode.normalizeLoudness` / `reduceNoise`:
  `reduceNoise` applies `afftdn=nf=-25` on the concat pass, and
  `normalizeLoudness` measures the joined file with `ebur128` and applies a
  static `volume` gain. **The gain is deliberately not applied by ffmpeg's
  `loudnorm` filter**: in ffmpeg 8 both its dynamic and its linear two-pass mode
  discard the first ~3 s of the stream, which silently eats the intro of every
  normalized episode (measured: 12.0 s in, 9.10 s out). `afftdn`, `volume` and
  `afade` were verified to preserve duration, so the measurement drives a
  `volume` filter instead. The gain is
  `min(target - measuredI, ceiling - measuredTP, maxGain)`, so a too-dynamic
  source ends up quieter than requested instead of clipping. Tuned through
  `PROGRAMS_LOUDNESS_TARGET` / `_CEILING` / `_MAX_GAIN`. At most two encoding
  passes: the measurement in between decodes without writing.
- **Two-step publish, so the admin hears it before it reaches the station.**
  `POST /:id/episodes/prepare` composes the episode and leaves it in
  `config.programs.tempDir/<episodeId>/episode.mp3` with status `draft`;
  AzuraCast is untouched. `POST /episodes/:episodeId/publish` uploads that
  exact file, writes metadata and artwork, and reserves the window. Composing
  is the expensive part and it is what the preview plays, so publishing only
  uploads the file that was already composed: the admin is never charged for
  ffmpeg twice. `GET /episodes/:episodeId/preview` streams it.
  Once the real duration is known the panel re-requests the slot, so the
  reserved window is exact instead of estimated from the file size.
  Changing any input discards the draft, and `discardStaleDrafts` (run by the
  `programs-archive` cron) sweeps previews nobody published after
  `PROGRAMS_DRAFT_TTL_HOURS`.
- Metadata is written right after the upload with `PUT /station/{id}/file/{id}`:
  `title` (the admin title, or the file name normalized by
  `shared/utils/text.ts` `titleFromFilename`: extension dropped, diacritics and
  punctuation become spaces, title-cased), `artist`/`album` defaulting to the
  program name, `genre`, and the playlist list in the same call. Artwork goes
  through `POST /station/{id}/art/{media_id}` with the program default or a
  per-episode image. AzuraCast exposes no writable date field, so the date lives
  in the library path and in `ProgramEpisode.uploadDate`.
- **Played detection is playlist membership, not history.** A sequential
  playlist drops an item once it is played, so `syncProgram` diffs the queued
  episodes against `GET /station/{id}/playlist/{id}/order` and treats the ones
  that are gone as aired. Episodes younger than
  `PROGRAMS_PLAY_GRACE_MINUTES` are skipped so a queue write AzuraCast has not
  reflected yet is not mistaken for a play. Re-adding the file by hand makes it
  play again, which is the correct behavior. Cron `program.playback.job.ts`
  every 5 min plus manual `programs-archive` from `systemJobs.registry.ts`.
- Scheduling has three modes per program: `none` (queue only),
  `auto` (`program.slotFinder.service.ts` picks the earliest free window that
  does not overlap ANY playlist schedule item of the station, with a per-program
  day mask, emission window and `bufferMinutes` reserved around other programs),
  `manual` (the admin sends `dayIndex` + `startTime` and it is validated the same
  way). Writing a window replaces the whole `schedule_items` array, so the
  untouched items are read back and resent. **A linked playlist that already has
  schedule items is never touched**: those items are the program airing pattern
  the station owner defined, so `auto`/`manual` step aside and the episode just
  queues into the existing programming.
- Endpoints (all `requireAuth` + permiso `programs`, mounted at
  `/admin-api/programs`): `GET|POST /`, `GET|PUT|DELETE /:id`,
  `POST|DELETE /:id/artwork`, `POST|DELETE /:id/assets/:kind` (`intro`|`outro`),
  `GET /:id/episodes`, `POST /:id/episodes/prepare`, `GET /:id/schedule`,
  `GET /:id/slot`, `POST /:id/slot/check`, `POST /:id/sync`,
  `POST /episodes/:episodeId/publish`, `GET /episodes/:episodeId/preview`,
  `POST /episodes/:episodeId/played|queued`, `DELETE /episodes/:episodeId`.
- The episode audio is written to disk by multer (`diskStorage`, 400 MB cap), not
  into memory. The preview goes through axios on the panel side instead of the
  route: `<audio>` cannot send the `Authorization` header, so the file is
  fetched as a blob and played from an object URL. A long episode is therefore a
  full-size download before playback, which is the price of keeping the token
  out of the URL.
- Local assets live in `backend/storage/program-assets` (intro/outro) and
  `backend/storage/program-art` (images, optimized to 600x600 WebP with sharp),
  served at `/media/program-art` and `/api/media/program-art`. The generic fs
  helpers were extracted to `shared/storage/localStorage.ts`;
  `notices/media/media.storage.ts` re-exports them.

## Voice engine: ElevenLabs pool with Kokoro fallback (Oct 2026)

Kokoro was good enough for a script but sounds robotic on air, so the
announcements are synthesized by ElevenLabs. The station does not pay for it,
so the answer is a pool of free accounts: each announcement takes the first key
that is free and falls back to Kokoro only when no key can answer.

- `synthesize()` in `locutor/tts.service.ts` is still the only entry point, so
  `audioGeneration.service.ts`, `playback.job.ts` and `locutor.routes.ts` did
  not change their call sites. It walks a fixed list of providers
  (`tts/tts.types.ts` `TtsProvider`): ElevenLabs first, then Kokoro. A provider
  that reports itself unavailable is skipped without spending a request, so a
  station with no key configured behaves exactly as before.
- `tts/apiKeyPool.service.ts` holds the key state, in memory, per process.
  **The three failures are not the same failure** and collapsing them into
  "key unusable" is the bug to avoid: `invalid_api_key` (401) parks the key for
  the process lifetime, `quota_exceeded` parks it until the reset date the
  provider reports via `GET /v1/user/subscription`, and anything else (429
  concurrency, 5xx, timeout) parks it for two minutes because it says nothing
  about the quota. Reservation is round-robin so credits spread evenly and a
  revoked key is noticed before it is needed; the lease carries an in-flight
  counter so two concurrent generations do not both spend the last key with
  credits. A restart re-probes every key once, which is the right trade for a
  station that announces a few times a day.
- **The template voice is provider-neutral and stays in the DB.**
  `AnnouncementTemplate.voice` keeps its Kokoro label (`ef_dora`); ElevenLabs
  maps it through `ELEVENLABS_VOICE_IDS` and falls back to
  `ELEVENLABS_DEFAULT_VOICE_ID`. So the panel still edits a two-option
  dropdown and the panel copy says it is the fallback voice. What was actually
  used is recorded on the audio as `elevenlabs:<voiceId>` / `kokoro:<voice>`.
- `speed` is shared, because both engines measure it the same way around 1.0,
  and ElevenLabs clamps it to 0.7–1.2. The template slider was narrowed to that
  range so it does not offer values that get silently clamped.
- **`GeneratedAudio.provider` is what makes the voice change audible.**
  `findReusableAudio` filters on the provider that would answer right now. A
  Kokoro recording left in the bank would otherwise keep being reused after
  ElevenLabs becomes available, and the station would sound robotic for weeks
  with nothing pointing at the cause. The cost of the switch is one generation
  per hour/group until the bank is repopulated with the new engine; the old
  rows are not deleted, they just stop being reused and age out through
  `expireOldAudios`. Migration
  `20261013000000_add_announcement_provider` defaults the column to `kokoro`,
  which is what every pre-existing row was.
- `voice_not_found` and `max_character_limit_exceeded` throw
  `TtsProviderConfigError` instead of parking a key: they would fail
  identically on every key, so the chain moves straight to the fallback.
- Admin endpoints: `GET /status` returns a `tts` block (preferred provider,
  last provider, fallback count since process start, per-key state and the
  credit balance) replacing the old `kokoro.healthy` flag, and
  `GET /test-tts` (was `/test-kokoro`) synthesizes a real phrase and reports
  which engine answered while refreshing the balance. Panel:
  `StatusDashboard.tsx` shows the engine, the key pool and the remaining
  characters; `AudioBank.tsx` badges each row with the engine that produced it.
  **The key value never leaves the backend**, only its last four characters.
- The credit balance is the number that decides how many keys the station
  needs. It is read from the subscription endpoint only when a quota failure
  happens or when an admin presses the test button, so it costs nothing on the
  normal path; the panel polls `/status` every 30 s without spending a request.
  **Measured 8 Oct 2026**: the free plan allows 10,000 characters per month and
  a 100-character announcement takes 6.7 s of audio. That is roughly 100
  announcements per account per month, so one key covers about two days of
  `LOCUTOR_ANNOUNCEMENTS_PER_HOUR=2`. The pool has to be sized against that
  number, and the cheapest lever is the bank: `findReusableAudio` refuses an
  audio used the previous day, so with exactly one audio per hour every
  announcement regenerates daily. Two or three per hour rotates the bank and
  cuts the monthly bill proportionally.
- The announcement text is sent to a third party. It contains the station name
  and the time, no listener data, but that is a deliberate choice and worth
  re-reading if a template ever interpolates something a listener wrote.
- `logs.service.ts` `LOCUTOR_LOG_KEYWORDS` lists the module's logger contexts
  and the engine names. Without `nightlyjob` the nightly job landed in the
  worker tab, because its context contains "job".

## Bible reading rotations (Sep 2026)

- Models: `PlaylistRotation` (`playlist_rotations`) + `RotationRunLog` (`rotation_run_logs`) in `prisma/schema/rotations.prisma`. Module `src/modules/rotation/` with `rotation.routes.ts`, `rotation.service.ts`, `bibleSource.service.ts`, `azuracastPlaylist.service.ts`, `rotation.job.ts`.
- Cron `rotation.job.ts` at 03:30 station time, plus manual runs from `systemJobs.registry.ts` (`rotations: runAllActiveRotations`).
- **Source order is canonical, not alphabetical.** `bibleSource.service.ts` resolves every audio to a Bible chapter from AzuraCast metadata (`album` = book name, `title` = "1 Reyes capitulo 4", file name as fallback), then sorts by `BibleBook.order` + `BibleChapter.number`. This matters: folder sources like `BIBLIA/OT` + `BIBLIA/NT` sort as NT-first under `path.localeCompare`, which is the reverse of reading order. Non-biblical rotations keep the natural source order (sequential playlist, or alphabetical paths for folders).
- `cursor` is the only mutable position. The announced chapter is read off the audio at `source[cursor]`, so the reading can never drift from what is played. `bibleStartOrdinal` still exists in the schema but is no longer read or written by the API — it used to derive the chapter as `bibleStartOrdinal + position`, which was wrong whenever the source order was not canonical.
- Files whose chapter cannot be resolved are kept at the end of the list in path order, excluded from the announced chapters, and reported through `unresolved` so the panel can show them instead of mis-announcing.
- Endpoints (all `requireAuth` + permiso `rotations`, salvo `GET /history` que usa `reading.history`): `GET|POST /admin-api/rotations`, `GET|PUT|DELETE /:id`, `POST /:id/run`, `GET /:id/runs`, `GET /:id/source` (posición real + próximos capítulos + `unresolved`), `POST /:id/align` (`{ book, chapter }` mueve el cursor y ejecuta la rotación de inmediato), `GET /admin-api/rotations/history`.
- `GET /api/bible/reading/today` is public and derives the reading from the last `RotationRunLog` of the current Bogotá day. It returns `null` when no run happened that day.
- **The source is cached for 10 minutes** (`bibleSource.service.ts`), keyed by source + translation, with in-flight de-duplication. Resolving a source walks the whole station library, which used to take long enough to trip the 10s admin request timeout: `listAllStationFiles` now reads the total from page 1 and fetches the remaining pages concurrently. Uploads and file deletes call `invalidateRotationSourceCache()`. The frontend gives `/source` and `/align` a 120s timeout instead of the default 10s.

## Worker auto-update (Sep 2026)

- Releases: `WorkerRelease` (version semver única, sha256, size, filePath) + `WorkerNode.version`. Artefacto ZIP en `backend/data/worker-releases/<version>.zip` (gitignore, máx 50 MB).
- Endpoints: `POST /admin/worker-releases` (multipart, requireAuth), `GET /admin/worker-releases`, `GET /workers/updates/latest` y `GET /workers/updates/:version/download` (auth `x-worker-secret` + verificación sha256).
- WS: mensaje `update_available {version, sha256, url, mandatory}` broadcast a workers conectados; worker reporta `version` en `register`. Worker solo aplica en `IDLE` (`activeJobs===0`), si está `busy` guarda pending y aplica al quedar idle. Polling fallback cada 6h.
- Worker updater: `worker/worker/src/updater.ts` descarga, verifica hash, descomprime a `.pending`, swap atómico, backup `main.js.bak`, `WinSW restart`.

## Health watchdog (Sep 2026)

- Module `src/modules/health/`: `health.checks.ts` (7 checks: AzuraCast, AutoDJ, workers, YouTube jobs, disk, backup, listener sampling), `health.service.ts` (in-memory state, alert dedup by (check,code), email/push notify with backoff, AutoDJ self-restart with backoff), `health.job.ts` (cron every `HEALTH_CHECK_INTERVAL_SECONDS`, default 120s), `health.routes.ts` (admin + public).
- Routes: `GET /admin-api/health/watchdog` and `POST /admin-api/health/watchdog/run` (requireAuth + `dashboard` permission), anonymous `GET /api/health/public` (aggregate `{status, checkedAt}` only, no internals). The watchdog lives under `/watchdog` so it does not shadow the plain liveness `GET /admin-api/health`, which now also reports the aggregate `status`.
- Push alerts go only to `HEALTH_PUSH_TOKENS`; the `Device` table is shared with the public app, so listener devices are never notified.
- Config in `src/config/health.config.ts` (thresholds, mount path, email/push toggles). Also registered in `systemJobs.registry.ts` as `health-watchdog` for manual runs from AdminJobs.
- Remediation policy: only AutoDJ restart is automatic (with backoff). Everything else notifies `EMAIL_RECIPIENTS` with a direct link to the affected panel area (`PANEL_PATH_BY_CHECK`: streaming, youtube, backups, dashboard) and the same URL travels in the push `data.url`. Alerts re-notify up to 3 attempts; recovery clears them.
- Live-streamer safety: `checkAutoDj` reports OK while `now_playing.live.is_live` is true (no alert, no remediation), and `attemptAutoDjRestart` re-checks `getPanelStatus().isLive` immediately before calling `start-autodj`, so the watchdog can never kick an on-air streamer off the stream.

## Behind nginx (trust proxy)

`app.set("trust proxy", 1)` in `backend/src/app.ts` assumes exactly one reverse
proxy hop. nginx must therefore send `X-Forwarded-For`
(`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`). Without this,
`req.ip` is `127.0.0.1` for every request and any IP-keyed logic degrades:
the login rate limiter (`auth.routes.ts`, 30 attempts / 10 min) becomes a single
global counter and locks out every admin at once. Hop count 1 is safe against
spoofing because nginx appends the real peer as the last entry, which is the one
Express reads.

## Ports

- HTTP: `PORT` (default 3001). WS worker server: `WS_PORT` (default 3001) — they must differ in production or the second listen fails with EADDRINUSE. This mirrors the original behavior.

## Backups (SQLite -> Cloudflare R2)

- `scripts/radio-backup.sh` — daily automatic backup via systemd timer
  (`scripts/radio-backup.timer`, 05:00 server time). Uses the SQLite backup
  API (safe in WAL mode while the backend runs), bundles `prisma/dev.db`
  with `data/worker-releases` and `storage/notice-{images,videos}`, uploads
  to R2 with size verification, and prunes old bundles locally and in R2.
- Retention: `BACKUP_KEEP_DAILY` (default 7) daily bundles plus
  `BACKUP_KEEP_WEEKLY` (default 4) Sunday bundles. Without R2 credentials
  the script still completes in local-only mode under `/var/backups/radio`.
- `scripts/radio-restore.sh` — restore with sha256 + `integrity_check`
  verification, a safety copy under `/var/backups/radio/pre-restore-*`,
  backend stop/start and health check. Dry usage:
  `sudo bash scripts/radio-restore.sh --from r2 --date 20260911`.
- Server config lives in Infisical (R2 keys, retention knobs), see
  `scripts/radio-backup.env.example` for the full list. The timer runs
  `backend/dist/run-backup.js`, which loads Infisical and then executes the
  backup script; `/etc/radio/backup.env` (mode 600) remains only as a
  fallback for values missing from the environment. Status of the last run
  is in `/var/backups/radio/last-backup.status`, logs in
  `/var/log/radio-backup.log`.
- Superadmin panel: `src/modules/backups/` exposes `GET /admin-api/backups`
  (status + retained bundles), `GET /admin-api/backups/log` and
  `POST /admin-api/backups/run` (spawns the script in background, 409 when
  busy). Guarded by `requireAuth` + `requireSuperAdmin`; paths come from
  `src/config/backups.config.ts`, never from user input.

## Playback history (Oct 2026)

A local mirror of what the station actually emitted. AzuraCast answers about
60 days of history over HTTP and nothing more; this module copies that window
into SQLite so the panel can page, filter and aggregate it without asking
AzuraCast for a 55 day range on every click.

- Model `PlaybackEvent` (`playback_events`) en `prisma/schema/playback.prisma`,
  migración `20261004000000_add_playback_events`. Módulo
  `src/modules/playback/`: `playbackHistory.ts` (captura),
  `playback.service.ts` (consultas y validación), `playback.routes.ts`,
  `playback.job.ts` (cron).
- **La metadata va copiada a la fila a propósito.** `title`, `artist`, `album`,
  `playlist`, `streamer` y `durationSec` se guardan junto al evento y no se
  resuelven contra la biblioteca: resolverlos exige paginar miles de archivos de
  AzuraCast, y el historial se consulta mucho más veces que la biblioteca. El
  índice por `song_id` existe solo para poder recuperar esa copia sin escanear la
  tabla entera (1,75 ms frente a 41 ms medido).
- **La ventana devuelta es semiabierta y la deriva `parseRange`.** El cliente
  nombra el último día cubierto en `to`, no un límite exclusivo, y el servicio
  es el único lugar que decide el tope. Toda ventana se mide en días de
  estación, no en milisegundos: 55 días de estación abarcan 55 días más o menos
  una hora según el cambio horario, y un tope en milisegundos haría inalcanzable
  el borde de la retención en medio del calendario.
- Endpoints (`requireAuth` + permiso `dashboard`, montados en
  `/admin-api/playback`): `GET /log` (bitácora cronológica paginada),
  `GET /audios` (agregado por `songId`, con `order=plays|recent|first`; la
  metadata se toma del play más reciente de cada audio para que editar la ficha
  dentro de la ventana no parta el contador) y `GET /filters` (los nombres de
  playlist que aparecen en la tabla, con diez minutos de caché porque solo
  llenan un desplegable).
- Cron `playback.job.ts` cada 5 minutos en `config.locutor.timezone`, más la
  corrida manual `playback-capture` de `systemJobs.registry.ts`, que aparece
  en el panel de Jobs como "Historial de reproducción".
- **La retención son 55 días y no 90 porque AzuraCast no tiene 90 días.**
  Medido contra la estación: conserva alrededor de 60. Prometer más dejaría la
  comprobación de cobertura insatisfecha para siempre, y cada corrida volvería
  a recorrer días que la estación ya no puede servir. El piso de retención se
  aplica en cada corrida con un `deleteMany` sobre `playedAt`.
- **`azuracastShId` es la clave de idempotencia y por eso no hay cursor
  guardado.** La ventana de cada corrida se solapa con la anterior a propósito
  (`POLL_OVERLAP_MS`, diez minutos), así que el mismo evento llega más de una
  vez; el índice único y el filtrado previo en `insertMissing` lo descartan.
  Guardar un cursor para evitar el solapamiento sería peor: una corrida fallida
  dejaría un hueco que nada cubre, mientras que el solapamiento se cura solo en
  la siguiente corrida.
- `fetchRange` descarta en el borde los registros sin `song.id` y cuenta cuántos
  descartó. `toRow` normaliza el resto: el contrato de AzuraCast declara
  `playlist`, `streamer` y `duration` como anulables aunque 17 689 registros
  reales en 55 días nunca lo fueron, y un solo `null` crudo abortaría el
  `createMany` del día entero. `SongHistory` en `packages/types/src` se mantiene
  no anulable a propósito: propagar el `null` tocaría a todos los demás
  consumidores del historial a cambio de proteger un caso que no ocurre.

## Intro y outro de programas especiales (Oct 2026)

Un programa especial entra al aire con un intro y sale con un outro, sin importar
cuántos archivos suenen adentro. Los de un solo archivo ya lo hacían por ffmpeg
(`programs`); estos son los que son una playlist de N archivos.

- Modelo `PlaylistBumper` (`playlist_bumpers`) en `prisma/schema/bumpers.prisma`.
  Módulo `src/modules/bumpers/` con `bumper.constants.ts`,
  `bumper.azuracast.service.ts`, `bumper.service.ts`, `bumper.routes.ts` y
  `bumper.job.ts`. Reutiliza el permiso `programs`, no crea uno nuevo.
- **AzuraCast hace el pegado, el backend solo ordena.** Una playlist con
  `source: songs`, `order: sequential` y `backend_options` con `merge` +
  `single_track` se emite fusionada en una sola pista: el generador de Liquidsoap
  de AzuraCast escribe `merge_tracks(...)` cuando `StationPlaylist.backendMerge()`
  es true, y `single_track` se traduce a `predicate.at_most(1, {ventana})`, o sea
  "la playlist se selecciona una vez dentro de su franja", **no** "suena un solo
  ítem". Por eso `merge` y `single_track` se escriben **juntos**:
  `computeBumperOptions` solo los agrega cuando `glued` es true. Con `glued: false`
  las opciones de la playlist quedan como el dueño las dejó, porque
  `single_track` a secas recorta una franja de noticias a un solo archivo.
- **La reconciliación es periódica, no de una vez.** `rotation.service.ts:179-203`
  **vacía y reconstruye** la playlist destino cada noche a las 03:30, así que un
  bumper fijado una sola vez desaparecería en la siguiente corrida. El cron corre
  cada 5 min (`BUMPERS_SYNC_CRON`) y se registra **después** de la rotación en
  `jobs/scheduler.ts`.
- **`merge` rompe la limpieza de noticias.** Al fusionar, el historial registra una
  sola entrada y los `song_id` de los archivos individuales dejan de aparecer, así
  que `cleanupNewsFolder` (`azuracast/cleanup/folderCleanup.service.ts`) no los
  reconoce como emitidos y la carpeta `NOTICIAS` crece sin límite. **Noticias debe
  quedar con `glued: false`.** Rehacer esa detección es un cambio aparte.
- **`priorBackendOptions === null` significa "sin snapshot"; `""` significa "la
  playlist no tenía opciones".** El snapshot se toma en la reconciliación *antes*
  de escribir las opciones, o no queda nada que devolver al deshabilitar o borrar.
- Los bumpers viven en `<PROGRAMS_ROOT_FOLDER>/BUMPERS/`, fuera de las carpetas por
  programa que recorre `programs-archive` y fuera de la ruta de noticias.
- Guardas de `POST /`: la playlist debe existir, no puede ser
  `AZURACAST_PLAYLIST_ID` (el contenido variado general: fusionarla uniría toda la
  música del día), no puede ser la playlist de un `Program` (sus episodios ya se
  pegan con ffmpeg) y no puede tener ya un bumper. Si `AZURACAST_PLAYLIST_ID` no es
  un id válido la guarda queda inactiva y se avisa por log: no es una protección
  silenciosa.
- Endpoints en `/admin-api/bumpers` con `requireAuth` + permiso `programs`:
  `GET /`, `POST /`, `PUT /:id` (acepta `label`, `enabled`, `glued` y `playlistId`),
  `DELETE /:id`, `POST|DELETE /:id/assets/:kind`, `POST /:id/reconcile`. El PUT
  devuelve la playlist anterior a su estado previo antes de enganchar la nueva.
- La subida de un bumper es de 80 MB y va a disco (multer `diskStorage`); el
  directorio temporal se limpia en **todos** los caminos de salida, incluidos los
  rechazos del propio multer, que ya habían escrito el archivo.

## Canales de YouTube desde el panel (Oct 2026)

La lista de canales que sigue la estación se administra en el panel admin, no en
el entorno. Es el primer paso de mover configuración a la base de datos.

- **La ingesta es un sondeo de la Data API v3, no WebSub.** Medido el 31 de
  octubre de 2026: `https://www.youtube.com/feeds/videos.xml` responde `404`
  para un canal real y para un id inventado, y
  `https://www.youtube.com/xml/feeds/videos.xml` responde `200` con los mismos
  463 bytes sin `<entry>` para ambos. El hub `pubsubhubbub.appspot.com` sigue
  devolviendo `202`, pero se emite antes de verificar el callback y el topic no
  tiene nada que publicar, así que la cadena push no puede entregar videos.
  `channelUploads.service.ts` consulta `playlistItems.list` sobre la playlist de
  subidas (`UC` → `UU`) y `subscription.service.ts` encola lo publicado desde que
  se agregó el canal. Requiere `YOUTUBE_API_KEY`; sin ella el canal queda
  `unverified` y el log lo dice. La suscripción al hub se conserva por si YouTube
  restaura el feed, pero no es el transporte que ingiere.
- **El webhook se monta antes que el router de administración, no después.** El
  router de admin lleva `router.use(requireAuth)` sobre todas sus rutas, así que
  montado primero responde `401` a la verificación del hub y la suscripción nunca
  se verifica: `GET /admin-api/youtube/webhook?hub.mode=subscribe&hub.challenge=X`
  devolvía `401 {"error":"No autorizado"}` (25 bytes, el cuerpo de
  `auth.middleware.ts:33`). Esto llegó con `13c9f45`, el 16 de octubre, y es
  independiente del topic: aunque el feed hubiera seguido vivo, el hub no habría
  podido suscribirse. Es fácil confundirlo con lo anterior porque
  `state: subscribed` en el panel tampoco lo detecta: solo refleja el `202`.
  `apps/web/tests/youtube/websub-wiring.test.ts` fija el orden.
- **El id del canal estaba mal escrito y la corrección es una migración.**
  `UCVqtvYvLNHvGymJFoGeRH7nw` (con una `v` de más y la `y` en minúscula) daba
  `404`; el real es `UCVqtYvLNHvGymJFoGeRH7nw`. La migración
  `20261018000000_fix_youtube_channel_id` corrige la fila y también
  `YouTubeVideo.channelId`, porque `channelCategoryOf()` busca la fila del
  registro al despachar y un job pendiente con el id viejo caería a la playlist
  general en vez de a la de noticias. También pone `expiresAt`, `feedEntryCount` y
  `feedCheckedAt` en `null`: describían el topic viejo, y con `expiresAt` en null
  la renovación del cron vuelve a suscribirse con el feed bueno en su próxima
  pasada.
- `YouTubeSubscription` pasó a llamarse `YouTubeChannel` (migración
  `20261017000000_youtube_channels`, que crea, copia y borra: SQLite no renombra
  preservando índices). Antes solo recibía un `upsert` al arrancar y nadie lo
  leía; ahora es la configuración. Por eso la columna `active` desapareció:
  "dar de baja un canal" borra la fila, no deja un tercer estado que el panel
  tenga que explicar.
- **`category` reemplaza a `YOUTUBE_CHANNEL_NOTICES`.** Es `GENERAL` o `NEWS` y
  decide carpeta y playlist en los dos caminos de subida:
  `workers/jobDispatcher.ts` elige la playlist y `workers/workerAdmin.routes.ts`
  elige la carpeta, los dos con `channelCategoryOf()` de
  `youtube/channel.service.ts`. Si divergieran, el video acabaría en la playlist
  de una categoría y en la carpeta de la otra; `apps/web/tests/youtube` lo fija.
- **`state` se deriva, no se guarda**: `failed` si hay `subscriptionError`,
  `unverified` si nunca se comprobó el feed, `expiring` si el lease vence dentro
  de `RESUBSCRIBE_MARGIN_MS` (6 h) y `subscribed` si no. Derivarlo evita que la
  base contenga un estado que contradiga sus propias fechas, y el margen es el
  mismo del cron para que el panel diga "por renovar" cuando el cron va a renovar.
- **`feedEntryCount` es el autodiagnóstico**: `null` = nunca comprobado, `0` =
  el feed respondió y no trae videos. El alta **no** se rechaza cuando el feed
  viene vacío — un canal existe aunque YouTube no avise, y bloquearlo dejaría al
  admin sin forma de registrarlo — sino que la fila queda con `0` y el panel lo
  dice.
- **La ingesta es un cron, no un `setInterval`.**
  `youtube/youtube.subscription.job.ts` corre `7,22,37,52 * * * *` (cada 15 min,
  en minutos no redondos a propósito) contra un lease de 24 h que se renueva
  cuando le quedan menos de 6 h. `index.ts` solo hace una pasada sin `await` al
  arrancar, para que un reinicio no espere al siguiente ciclo. También está en
  `systemJobs.registry.ts` como `youtube-subscriptions`.
- **Borrar un canal borra la fila primero y avisa al hub después.** El orden
  inverso dejaría una fila que el hub ya no sirve y que nadie puede volver a
  suscribir. Si el unsubscribe falla, la fila sigue borrada y el error va al log.
  Los videos recibidos no se borran: son historial de emisión.
- **El webhook descarta notificaciones de canales no registrados** (quedan en el
  `YouTubeChannel`), porque el hub sigue empujando hasta 24 h después de borrar
  el canal y sin esta guarda el material de un canal retirado se seguiría
  emitiendo al aire. El `200` va antes de todo, así que el hub no reintenta.
- `parseChannelId` vive en `youtube/channelId.ts` y no en el servicio: el backfill
  lo necesita y este importa `config`, que lanza en el import si falta cualquier
  variable requerida. Un script que solo escribe filas no debería arrastrar toda
  la configuración.
- **`YOUTUBE_CHANNEL_IDS` y `YOUTUBE_CHANNEL_NOTICES` se eliminaron**, junto con
  `config/youtube.config.ts`. Antes de desplegar hay que correr **una vez**
  `pnpm --filter @radio/backend youtube-channels:backfill`, que lee las dos
  variables del entorno y escribe las filas; sin eso la ingesta se detiene en
  silencio. Después se borran las dos de Infisical. `tests/youtube` falla si
  alguna vuelve a aparecer fuera del backfill.
- Endpoints en `/admin-api/youtube` con `requireAuth` + permiso `youtube`:
  `GET /channels`, `POST /channels`, `DELETE /channels/:channelId`,
  `POST /channels/:channelId/resubscribe`. El webhook se monta **antes** que el
  router de administración en `app.ts`, nunca al revés: ver la trampa del `401`
  más arriba.
